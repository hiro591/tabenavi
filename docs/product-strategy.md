# たべなび プロダクト戦略書

## サービスピボット宣言

**旧方向性**: 食事管理・ログアプリ（記録が目的）
**新方向性**: 体型管理中の人のための、外食・コンビニ・スーパー商品発見サービス（発見が目的）

**一言で言うと**: 「食べたい気分」と「栄養目標」を入力するだけで、今すぐ買える・食べられる最適な選択肢が見つかるサービス。

---

## 1. ターゲットユーザー定義

### プライマリターゲット

**「意識はしてるけど、毎回悩む人」** — 20〜40代の体型管理中の社会人

| 属性 | 詳細 |
|------|------|
| 年齢 | 25〜39歳（コア層） |
| 性別 | 男女問わず（ただし初期は筋トレ・ダイエット層に集中） |
| ライフスタイル | 平日は外食・コンビニ中心、自炊は週末のみ |
| 体型管理の段階 | 「なんとなく気をつけている」〜「マクロ管理をしている」 |
| ITリテラシー | スマホネイティブ、アプリに抵抗なし |

### ペインポイント（具体的な不満）

1. **「結局いつも同じものを選んでしまう」** — サラダチキンとブロッコリーに飽きた。でも他に何がいいかわからない。
2. **「栄養情報を調べるのが面倒すぎる」** — チェーン店のメニューを1つずつ公式サイトで確認するのは現実的でない。
3. **「食べログや Google で探しても栄養情報が出ない」** — 味の評価はあっても、カロリーやPFCで絞り込めない。
4. **「あすけんは記録アプリであって、発見アプリではない」** — 食べた後に記録するのは苦痛。食べる前に選択肢を出してほしい。
5. **「コンビニの新商品、どれが自分に合うかわからない」** — 毎週新商品が出るが、裏面を全部チェックする時間はない。

### Jobs to Be Done

- **ランチ前**: 「今日のランチ、タンパク質30g以上でカロリー600kcal以内のもの、近くで何がある？」
- **コンビニ到着時**: 「今日あとタンパク質20g必要。500円以内で最適な組み合わせは？」
- **夕食の外食選び**: 「今日はがっつり食べたいけど、脂質は抑えたい。近くのチェーン店で何がある？」
- **スーパーでの買い物**: 「明日の弁当用に、高タンパク低脂質のおかずになる惣菜は？」

## 2. 競合分析

### 既存サービスの比較

| サービス | 強み | 弱み | たべなびとの違い |
|----------|------|------|------------------|
| **あすけん** | 食事記録のUI、AI栄養士、ユーザー数 | 記録が目的。発見機能なし。「何を食べるか」は教えてくれない | たべなびは「食べる前」に使う |
| **カロミル** | 写真認識の精度、細かい栄養素 | 同上。記録特化 | 同上 |
| **MyFitnessPal** | 巨大なフードDB、バーコードスキャン | 日本のチェーン店・コンビニ商品のカバー率が低い。UIが複雑 | 日本市場に特化した商品DB |
| **食べログ** | 口コミ、店舗網羅性 | 栄養情報ゼロ。味と雰囲気の評価のみ | 栄養×気分で検索できる |
| **マクドナルド公式等** | 自社メニューの栄養情報は正確 | 自社のみ。比較ができない | チェーン横断で比較できる |

### 市場のギャップ

**「栄養目標を持つ人が、食べる前に最適な選択肢を発見できるサービス」は存在しない。**

- 記録アプリは「食べた後」にフォーカス
- グルメアプリは「味・雰囲気」にフォーカス
- 栄養情報は各社バラバラに散在

→ たべなびは、この3つの間にあるブルーオーシャンを狙う。

## 3. コアバリュープロポジション

### ワンセンテンス

> **「食べたい気分を入力するだけで、あなたの栄養目標に合う外食・コンビニ・スーパーの選択肢が一瞬で見つかる。」**

### なぜ Google / 食べログ / Instagram ではダメなのか

| 既存手段 | 限界 |
|----------|------|
| Google検索 | 「高タンパク ランチ 渋谷」→ まとめ記事が出るだけ。リアルタイムの在庫や栄養情報と紐づかない |
| 食べログ | 「タンパク質30g以上」で絞り込めない |
| Instagram | 見た目はわかるが栄養情報がない。広告・PR投稿が多い |
| あすけん | 食べた後の記録。「何を食べるべきか」は教えてくれない |

**たべなびだけが提供する価値**: 栄養目標 × 気分 × 場所 × 予算 を掛け合わせた「パーソナライズされた食の発見体験」

## 4. コアユーザーフロー

### 理想の3ステップ

```
Step 1: 気分・条件を入力（3秒）
  「何が食べたい？」→ ジャンル/気分タグをタップ
  + 栄養条件は事前設定済み（プロフィールから自動適用）

Step 2: 選択肢が一覧表示（即時）
  外食・コンビニ・スーパーの選択肢がカード形式で表示
  栄養情報・価格・距離がひと目でわかる

Step 3: 選んでアクション（1タップ）
  → 地図で場所を確認 / メニュー詳細を見る / お気に入り保存
```

### 詳細フロー

#### 初回利用時（オンボーディング）
1. 目的を選択: 「ダイエット」「筋トレ・バルクアップ」「健康維持」「特になし」
2. 基本情報入力: 身長・体重・目標体重（任意）
3. 1日の栄養目標を自動計算（手動調整可能）
4. よく使うカテゴリを選択: 「コンビニ」「チェーン外食」「スーパー」

#### 通常利用時
1. アプリを開く → メイン画面 = 検索/発見インターフェース
2. 気分タグを選択（複数可）:
   - 気分: 「がっつり」「さっぱり」「あったかい」「冷たい」「甘いもの」
   - ジャンル: 「和食」「中華」「洋食」「麺類」「丼もの」「パン・サンドイッチ」
   - シーン: 「ランチ」「間食」「トレ後」「夜食」
3. フィルター適用（事前設定 or 手動調整）:
   - カロリー上限
   - タンパク質下限
   - 脂質上限
   - 予算上限
   - カテゴリ（外食 / コンビニ / スーパー）
4. 結果表示:
   - カード形式で一覧（写真・商品名・栄養サマリー・価格・場所）
   - ソート: おすすめ順 / タンパク質多い順 / カロリー低い順 / 価格安い順 / 距離近い順
5. 詳細画面:
   - 完全な栄養情報
   - 同じ店の他のおすすめ
   - 「これに合わせるなら」（サイドメニュー・飲み物のレコメンド）

## 5. データ戦略

### 必要なデータ

| カテゴリ | データ項目 | 優先度 |
|----------|-----------|--------|
| チェーン外食 | メニュー名、カロリー、PFC、価格、店舗位置 | 最高 |
| コンビニ商品 | 商品名、カロリー、PFC、価格、取扱チェーン | 最高 |
| スーパー惣菜 | 商品名、カロリー、PFC、価格 | 中 |
| メタデータ | ジャンルタグ、気分タグ、季節フラグ | 高 |

### データ取得方法

#### Phase 1（MVP）: 手動キュレーション + 構造化

- **チェーン外食（20チェーン）**: 公式サイトの栄養情報ページから手動で構造化データを作成
  - 優先チェーン: 松屋、吉野家、すき家、CoCo壱番屋、大戸屋、やよい軒、サブウェイ、マクドナルド、モスバーガー、ケンタッキー、餃子の王将、日高屋、リンガーハット、丸亀製麺、はなまるうどん、なか卯、てんや、ガスト、サイゼリヤ、バーミヤン
- **コンビニ商品（3チェーン × 主要カテゴリ）**: セブン、ローソン、ファミマの弁当・おにぎり・サラダ・パン・プロテイン商品
  - 公式サイト + 実店舗での確認
  - 初期は各チェーン50〜100商品を目標

#### Phase 2: 半自動化

- 公式サイトからのスクレイピングパイプライン構築（定期更新）
- ユーザーからの商品登録・修正リクエスト機能
- バーコードスキャン → 栄養情報DB（Open Food Facts等）との連携

#### Phase 3: スケール

- チェーン店との公式データ連携（API）
- ユーザー投稿による商品DB拡充（レビュー・写真）
- スーパー各社のPB商品データ連携

### 最小実行可能データセット（MVP）

- **チェーン外食**: 10チェーン × 主要メニュー20品 = 200メニュー
- **コンビニ**: 3チェーン × 50商品 = 150商品
- **合計: 約350アイテム** でローンチ可能

## 6. 差別化機能アイデア

### 6-1. 気分ベースフィルタリング

既存サービスにない「気分」での検索。

```
「今日はがっつり食べたい」 → 高カロリーだけどPFCバランスが良いメニューを提案
「さっぱりしたい」 → 低脂質・さっぱり系メニューを提案
「甘いものが食べたい」 → プロテインバー、ギリシャヨーグルト等を提案
「疲れた、元気出したい」 → ビタミンB群が多い食事を提案
```

### 6-2. 栄養目標連動レコメンド

ユーザーの1日の栄養目標と、既に食べたもの（任意記録）から残りの栄養素を計算し、「あとタンパク質Xg」に最適な選択肢を提案。

```
例: 「今日あとタンパク質25g、カロリー500kcal以内」
→ セブンのサラダチキン(24g) + おにぎり(5g) = 29g、合計420kcal
→ 松屋の牛めしミニ(22g) + 味噌汁(3g) = 25g、合計480kcal
```

### 6-3. コンビニ組み合わせ最適化（キラー機能）

**「コンビニで予算X円以内、タンパク質Yg以上の最適な組み合わせ」を自動提案。**

これは他のどのサービスにもない。

```
入力: セブンイレブン、予算600円、タンパク質25g以上、カロリー600kcal以内
出力:
  組み合わせA: たんぱく質が摂れるチキン&スパイシーチリ(26.1g) + 味噌汁(2.1g) = 562円、28.2g、487kcal
  組み合わせB: サラダチキン(24.1g) + 玄米おにぎり(4.2g) + 味噌汁(2.1g) = 556円、30.4g、389kcal
  組み合わせC: プロテインバー(15g) + ゆで卵2個(13g) + サラダ(3g) = 590円、31g、410kcal
```

### 6-4. クロスカテゴリ検索

外食・コンビニ・スーパーを同時に検索。「今の自分の条件に一番合う選択肢」をカテゴリ横断で比較できる。

### 6-5. 時間帯・季節レコメンド

- 朝 → 朝食メニュー・モーニングセットを優先
- 昼 → ランチメニュー・ランチセット
- 夜 → 定食・セットメニュー
- 夏 → 冷たい麺・さっぱり系
- 冬 → 鍋・あったか系

### 6-6. 予算制約付き検索

「500円以内」「1000円以内」で絞り込み。コンビニとチェーン店の価格比較も可能。

### 6-7. 「チートデイモード」

体型管理中でも、たまには好きなものを食べたい。チートデイ用に「カロリー気にせず、満足度が高いメニュー」を提案。罪悪感なく楽しめるUI演出。

## 7. フェーズ別ロードマップ

### Phase 1: MVP（1ヶ月）— コンセプト検証

**ゴール**: 「この検索体験は価値がある」を10人のテストユーザーで検証

**スコープ**:
- [ ] 気分タグ選択 → 検索結果一覧表示の基本フロー
- [ ] チェーン外食10店 × 主要メニュー20品のデータ投入
- [ ] コンビニ3チェーン × 50商品のデータ投入
- [ ] 基本フィルター（カロリー・タンパク質・価格）
- [ ] レスポンシブWebアプリ（Next.js、既存基盤を活用）
- [ ] ユーザープロフィール（栄養目標設定）

**やらないこと**:
- 位置情報連動
- 組み合わせ最適化
- ユーザー登録なしでも使える（認証はPhase 2以降で必須化）

**技術スタック**:
- フロントエンド: Next.js（既存）
- バックエンド: Supabase（既存）
- データ: Supabaseのテーブルに直接投入

### Phase 2: コア差別化機能（3ヶ月）

**ゴール**: 「毎日使いたい」と思えるレベルにする

**スコープ**:
- [ ] コンビニ組み合わせ最適化機能
- [ ] 栄養目標連動レコメンド（残り栄養素 → 提案）
- [ ] 位置情報連動（近くの店舗を優先表示）
- [ ] チェーン店データ拡充（30チェーン）
- [ ] コンビニ新商品の定期更新フロー構築

### Phase 3: スケール・成長（6ヶ月）

- [ ] ユーザー投稿による商品情報拡充

## 8. マネタイズ戦略

### 短期（Phase 1-2）: 無料で成長

ユーザー獲得に集中。全機能無料。

### 中期（Phase 3）: フリーミアムモデル

| プラン | 価格 | 内容 |
|--------|------|------|
| 無料 | ¥0 | 基本検索、1日5回まで組み合わせ提案、広告あり |
| プレミアム | ¥480/月 | 無制限検索、組み合わせ最適化、広告なし、詳細栄養分析、お気に入り無制限 |

### 長期: 複数収益源

1. **B2C サブスクリプション** — プレミアムプラン（メイン収益）
2. **アフィリエイト** — コンビニ商品のEC購入リンク（Uber Eats、出前館等への送客）
3. **B2B チェーン店パートナーシップ** — 「おすすめ」として上位表示する広告枠（ネイティブ広告）
4. **データインサイト販売** — 「体型管理層がどんな食事を求めているか」の匿名化データ

**注意**: B2B広告は「ユーザーの信頼」を損なわない範囲に厳格に限定する。栄養的に基準を満たさないメニューは広告でも上位表示しない。

**旧UI（ログアプリ）**: ダッシュボード → 今日の記録 → 栄養グラフ

```
│  └───────────────────────────┘ │
│                                 │
├─────────────────────────────────┤

│  [プロフィール]                  │
└─────────────────────────────────┘
```

### デザイン原則

1. **「3タップ以内に結果」** — 開いて、気分を選んで、結果が出る
2. **「数字は見せるが、主役ではない」** — 栄養情報は重要だが、UIの主役は「おいしそうな写真」と「これ食べたい！」という感情
3. **「記録の強制ゼロ」** — 記録は任意。記録しなくても発見機能は100%使える
4. **「ポジティブなトーン」** — 「カロリーオーバーです！」ではなく「この組み合わせなら目標ぴったり！」

### 検索結果カードのデザイン

各カードに表示する情報（優先順）:
1. 商品名 / メニュー名
2. 提供元（チェーン名 / コンビニ名）
3. カロリー・PFC（コンパクトに）
4. 価格
5. 距離（位置情報ON時）
6. 気分タグ（マッチした理由）

## 10. サービス名・ブランディング

### 「たべなび」は新方向性にフィットする

- **たべる + ナビゲート** = 食の選択をナビゲートする
- 旧方向性（記録）では「ナビ」の意味が弱かったが、新方向性（発見・案内）では「ナビ」がまさに本質
- 覚えやすく、日本語として自然
- **結論: サービス名は変更不要。むしろ新方向性のほうが名前に合っている。**

### ブランドトーン

- **ポジティブ**: 制限ではなく発見。我慢ではなく最適解。
- **カジュアル**: 栄養管理の「堅苦しさ」を排除。友達に「これいいよ」と勧められる感覚。
- **信頼できる**: データは正確。根拠のある提案。
- **タグライン案**: 「食べたいものを、賢く選ぼう。」

### ビジュアルアイデンティティ

- メインカラー: 温かみのあるオレンジ〜コーラル系（食欲を刺激しつつ、ヘルシーさも感じる）
- サブカラー: クリーンなホワイト + ライトグレー
- アイコン: コンパスモチーフ（ナビ）× 食のアイコン

## 付録: MVP時点で必要なDBスキーマ（概要）

```sql
-- 商品・メニューマスタ
menu_items (
  id, name, chain_id, category,
  calories, protein, fat, carbs,
  price, image_url,
  mood_tags[], genre_tags[], scene_tags[],
  available_from, available_until,
  source_type (chain_restaurant | convenience_store | supermarket),
```
