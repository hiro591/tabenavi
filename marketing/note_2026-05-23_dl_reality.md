# 個人開発で外食ダイエットアプリを作って2週間、DL 14 / 登録 5 の現実

## はじめに

「いいアプリ作れば、勝手にユーザーが来る」

そう信じて、Next.js と Supabase で個人開発に挑戦した結果、**ダウンロード 14 / 登録ユーザー 5**でリリース3週間が終わりました。

この記事は、たべなび（@tabenavi_app）という外食ダイエット向け栄養管理アプリを個人で作って公開した、**「現実とぶつかった21日間」の全部**です。

数字は全部本物。良いとこも悪いとこも盛らずに書きます。これから個人開発を始める人、もしくは「リリースしたのに伸びない…」と落ち込んでる人の参考になれば嬉しいです。

## 🚀 たべなびって何？

ざっくり言うと、**外食しながらダイエットしたい人のためのアプリ**です。

- 22チェーン・6,000メニューのカロリー・PFC が登録なしで検索可能
- マクドナルド、吉野家、サイゼリヤ、コンビニ3社、サブウェイ、ゼッテリア…
- 全データを各社公式サイトから取得・検証

きっかけは、自分が3年前に体重86kg のデブだった時に「外食しか選択肢ない時、何選べばいいか毎回迷う」のがしんどすぎたことでした。

「外食 = 太る」じゃなくて、「外食 = 知らないから太る」なんですよね。データを見れば、サイゼリヤの若鶏のグリル（ディアボラ風）は500円でタンパク質35g。これを知ってる人は、知らない人より絶対に痩せる。

「全部のチェーンの数字、一箇所で見れたら楽じゃね？」と思って、作りました。

## 🔥 リリース直後の地獄: DL 7 / 登録 0

リリース後の1週間、私のアプリはこういう状態でした：

- ダウンロード: **7**
- 登録ユーザー: **0**（はい、ゼロです）

要するに、**100% のユーザーがダウンロードした後に離脱**していたんです。

「マーケが足りない」「広告打つしかない」「機能が悪いんだ」「俺には才能がない」

色んなことを考えました。色んな自分を責めました。

でも数日後、たまたまアプリを実機で確認した時に気づきました。

### 「**アプリ開いた瞬間に、強制ログイン画面**じゃん」

```typescript
// proxy.ts (Next.js middleware)
const protectedPaths = [
  "/search",     // ← ここがアウトだった
  "/items",      // ← ここも
  "/dashboard",
  // ...
];

if (!user && isProtected) {
  return NextResponse.redirect(new URL("/login", request.url));
}
```

ダウンロードしたユーザーは：
1. アプリを開く
2. 「メニュー検索」をタップ
3. **メアド + パスワード入力を求められる**
4. 「何これ、面倒くさ」で離脱

そりゃ誰も登録しませんよね。**価値を体験する前に登録を要求**していたんです。

これは個人開発でめちゃくちゃやりがちなミスです。「機能を使うには登録が必要」と思い込んでいる開発者、めちゃくちゃ多い。

### 修正：たった2行のコード変更

```typescript
// Before
const protectedPaths = ["/search", "/items", "/dashboard", ...];

// After
const protectedPaths = ["/dashboard", ...]; // /search と /items を削除
```

これだけ。**2行のコード変更で、ユーザー体験が180度変わりました**。

修正後の体験：
1. アプリを開く
2. 「ビッグマック」と検索
3. **すぐに 525kcal / P26g / F28g / C42g が表示**
4. 「食事を記録」をタップ → ここで初めてログイン誘導

「価値を体験 → 登録誘導」の流れ。これが正解だった。

修正後の24時間で、**初の登録ユーザー（自分以外の人）**が出ました。

## 📲 SNS の試行錯誤

DL を増やすには、まずアプリの存在を知ってもらう必要があります。

私は3つのチャネルを並行運用しています：

### Instagram リール

平日昼に撮影、夜編集して投稿。1日1本ペース。

**結果**: 2投稿で平均 200 視聴

「全然ダメじゃん…」と思いそうになりますが、調べてみると **新規アカウントの最初の10本は全部このレベル**なのが普通でした。

伸びるアカウントは「最初の30本でフォーマット模索 → 勝ちパターンを2-3週続けて伸びる」のがセオリーらしいです。

つまり、続けるしかない。

### TikTok

同じリール動画を、IG投稿と同時に TikTok にも上げています。**追加の手間ゼロ**。

新規アカウントの初動は TikTok の方が IG より強い、というのが個人開発界隈の通説。実際、500-1,000 視聴のものも出始めました。

### X（旧Twitter）

Build in Public スタイルで運用中。

- 朝 or 夜の1日1投稿
- 数字をリアルに公開
- 失敗も成功も両方書く
- ハッシュタグは原則ゼロ（2026年のアルゴリズム的に不要）

直近の人気投稿：

## 🐛 やらかした失敗集

ここまでに何回も泣きました。代表的なやつ紹介します。

### 1. Supabase の暗黙 limit 1000 でデータ重複挿入

データ反映スクリプトで「DB の既存アイテムを取得 → シートとマージ」する処理を書いた時、Supabase の `.select()` がデフォルトで 1000 件制限あるのを知らず：

- 1回目の実行: 正常
- 2回目の実行: 既存アイテム1,000件しか取れない → 残りを「新規」と誤判定 → **1,577件の重複挿入**

DB に同じメニュー2件並んでる状態を見て、夜10時くらいに絶望しました。

対処: 別スクリプトでクリーンアップ。同名・同栄養の重複を「最古を残して削除」。

### 2. Vercel CPU 上限到達

Google Search Console にサイトマップ（4,400 URL）を提出した翌週、Vercel から「無料枠の Fluid Active CPU 100% 到達」の警告メール。

Googlebot が4,000+ページをガンガンクロールしてくれた結果、SSR の CPU 消費が爆増。

対処: ISR（Incremental Static Regeneration）を導入。

```typescript
// items/[id]/page.tsx
export const revalidate = 86400; // 24時間キャッシュ
```

これで CPU 消費が **95%削減**。同じページに何回 Googlebot が来ても、1日1回しか再生成しない。

### 3. iPad で OAuth 認証が落ちる

App Store 審査で iPad テスト中、Apple のサインインで SFSafariViewController がポップアップで開いて落ちる。

調査したら、iPad だと `presentationStyle: "popover"` がデフォルトで、これが死亡。

対処: `"fullscreen"` に変更したけど結局 OAuth 自体を v1.0 から削除。複雑性を捨てる勇気が必要だった。

## 💡 個人開発21日で学んだ5つ

### 1. 「価値を見せる前に登録要求」は死亡フラグ

DL の何割が登録するか（活性化率）は、最初の30秒で決まる。検索バーを5秒で触れない設計は終わってる。

### 2. SNS は「最初の30本は捨て試合」

2-3本でフォロワーゼロでも普通。**続ける1%が結果出す**。

### 3. 失敗開示が最強のマーケ

「DL 7 / 登録 0」を晒したら、自慢投稿より反応取れた。**個人開発界隈の共感経済**を信じる。

### 4. データ整備はコードの3倍時間かかる

スクレイピング、検証、重複削除、UI 反映確認…全部含めると、実装より長い。**戦略の核心がここにある**。

### 5. Vercel 無料枠は SEO 強化で簡単に上限突破する

Googlebot が大量クロールすると CPU 消費爆増。**ISR / SSG は必須スキル**。
